# Исследование 05 — вёрстка под планшет и альбомную ориентацию, кривой код Tribit

> **Создан:** 2026-10-16 · **Родитель:** researches/03_tribit_app_pains.md · **Статус:** разведка · **Вовне:** —

Разведка по коду, на Титане ничего не проверялось. Пути кода даны от `decompiled/jadx-base/sources/`,
ресурсы и smali от `work/base/`. **`work/base` уже пропатчен** (`apply.py`: там есть `attachBaseContext`
и `krinik_icon_bg`), поэтому исходный код Трибита сверялся по jadx. Все подсчёты сделаны скриптами в конце
документа. Высоты разметок посчитаны эвристикой: она складывает размеры в dp и даёт порядок величины,
а не точное число.

## Главная находка: экраны подгоняет библиотека AutoSize, и патч 3 её не перебивает

В приложении стоит **AndroidAutoSize** (`me.jessyan.autosize`). Включает её провайдер
`AndroidManifest.xml:400`, базовый макет `design_width_in_dp=375`, `design_height_in_dp=667`
(`AndroidManifest.xml:216–217`). Настройки по умолчанию, только `setUseDeviceSize(false)`
(`me/jessyan/autosize/InitProvider.java:44`). Сам Трибит библиотеку нигде не вызывает: ни `CancelAdapt`,
ни `CustomAdapt`.

Как она работает. На **каждом** экране в `onActivityCreated`/`onActivityStarted` библиотека переписывает
`DisplayMetrics.density = ширина_экрана_px / 375` (`AutoSize.java:124`, `ActivityLifecycleCallbacksImpl.java:44–63`).
Отсюда три следствия:

1. **Системный масштаб (480 dpi) на вёрстку не влияет вообще.** Плотность считается из пикселей:
   при любом масштабе Титан в портрете получает 1600/375 = **4,27 px на dp**. Экран для вёрстки получается
   375 dp в ширину и (2560 − статус-бар − нав-бар)/4,27 ≈ **545–585 dp** в высоту. Телефон 1080×2400
   при той же формуле даёт ≈ 800 dp. Обрезает не масштаб, а **соотношение сторон 16:10**: макет нарисован
   под 375×667 и выше, а у планшета под вёрстку остаётся меньше 667 dp.
2. **Патч 3 почти бесполезен.** `BaseActivity.onCreate` сначала зовёт `super.onCreate`
   (`base/BaseActivity.java:57–58`), там AutoSize переписывает плотность, и только потом идёт
   `setContentView`. Плотность, которую поставил `attachBaseContext`, затирается до того, как разметка
   развернётся. Патч 3 меняет только выбор ресурсов (`sw600dp`, папки картинок), а своих `sw600dp`-разметок
   у Трибита нет. Проверить на Титане: в logcat с тегом `AndroidAutoSize` библиотека пишет
   `targetDensity`/`targetScreenHeightDp` для каждого экрана (`setLog(true)`).
3. **Альбомная ориентация ломается именно здесь.** В альбомной ширина 2560 px, плотность становится
   2560/375 = **6,83**, высоты остаётся (1600 − панели)/6,83 ≈ **200–230 dp**. Всё огромное, видна
   полоска экрана.

**Лечение одним патчем (патч A).** Пусть AutoSize вписывает макет 375×667 целиком, а не только по ширине:
если экран шире пропорции 375:667, считать плотность по высоте. Для этого достаточно заменить тело
`AutoSizeConfig.isBaseOnWidth()` (`smali_classes4/me/jessyan/autosize/AutoSizeConfig.smali:867`) на
`return getScreenWidth()*designH <= getScreenHeight()*designW`. Размеры экрана библиотека сама обновляет
при повороте (`AutoSizeConfig.java:126–135`), так что формула пересчитается. Что получится:
телефоны вытянутее 16:9 не изменятся, у телефонов ровно 16:9 всё станет мельче примерно на 3 %;
Титан в портрете получит ≈ 440×667 dp, то есть ровно макет
дизайнера; в альбомной ≈ 1150×667 dp — растянуто вширь, но ничего не обрезано.

## 1. Ориентация

Подсчёт `s1_manifest.py`:

| Что | Число |
|---|---:|
| Экранов (`<activity>`) в манифесте | 165 |
| Из них свои (`com.thousandshores.*`) | 146 |
| `screenOrientation` у своих экранов | **0** |
| `screenOrientation="portrait"` у чужих | 3 (`PickActivity`, `UCropActivity`, `UCropMultipleActivity`) |
| `screenOrientation="portrait"` на `<application>` | 1 (`AndroidManifest.xml:60`) |
| `setRequestedOrientation` в своём коде | 5, все про камеру PictureSelector, экран не запирают |
| Свои экраны с `configChanges` | 2 (`VideoPlayerActivity`, `UtilsTransActivity`) |
| Свои экраны с `onSaveInstanceState` | 1 (`UtilsTransActivity`, служебный) |
| Свои экраны с `onConfigurationChanged` | 16 (все `Bts*Control*` и `*Setting`) |

- **Запереть хотели, но не заперли.** `android:screenOrientation="portrait"` записан на `<application>`,
  а Android читает этот атрибут только у `<activity>`. Приложение поворачивается вслед за системой.
  В исследовании 03 насчитано четыре запертых экрана: четвёртым посчитан этот атрибут.
- **Нет альбомной** — это не запрет поворота, а AutoSize (см. выше): в альбомной высота ≈ 220 dp.
- **Android 16 и `targetSdk 36`:** на экранах с `sw ≥ 600dp` система сама игнорирует запреты ориентации.
  Титан при 480 dpi даёт sw = 533 dp, это меньше 600, поэтому запреты пока соблюдаются. При 320 dpi
  sw будет 800 dp, и запреты перестанут работать.

**Что сломает поворот.** Ни один свой экран не сохраняет состояние, и у всех нет `configChanges`.
Значит, при повороте каждый экран уничтожается и создаётся заново.

- `onConfigurationChanged` в 16 экранах колонок — мёртвый код. Например, `Bts56ControlActivity.java:2315`
  ждёт поворота, но в манифесте нет `configChanges`, и вместо вызова экран пересоздаётся.
- Пересоздание `Bts56ControlActivity` (главная страница колонки владельца) проходит через `onDestroy`
  (`:2278`): сбрасываются статические `isUpgrade`/`hasReset`/`current`, отписывается EventBus.
  Потом `afterCreate` заново опрашивает колонку (батарея, версия, эквалайзер). Это мигание и лишний
  трафик Bluetooth, но не поломка.
- **Опасно:** экраны с обновлением прошивки, 16 `*InfoActivity` (у Blast 2 это `Bts56InfoActivity`:
  `bts56OtaStart`, `dspOta`). Пересоздание посреди прошивки сбросит её состояние.
- Редактор эквалайзера (`Eq56DetailActivity`) берёт значения из intent: при повороте несохранённые
  полосы пропадут. Текст в полях входа и регистрации уцелеет: поля с `id` система сохраняет сама.
- Открытые окна загрузки и «Reconnecting» при пересоздании утекают (`WindowLeaked`), и состояние
  переподключения теряется.

**Совет:** поворот разрешить (после патча A), а 16 `*InfoActivity` дать
`configChanges="orientation|screenSize|screenLayout|smallestScreenSize"`, чтобы прошивку не прерывало.
`screenOrientation="locked"` хуже: при sw ≥ 600 Android 16 его не соблюдает.

## 2. Вёрстка

Подсчёт `s3_layouts.py`, `s6_textsize.py`:

| Что | Число |
|---|---:|
| Разметок в `res/layout` | 504 |
| Своих (на них ссылается код Трибита, плюс их `<include>`) | 272 |
| Экранов (`activity_*`, `fragment_*`) | 157 |
| …корень прокручивается (ScrollView/NestedScrollView/RecyclerView) | 7 |
| …прокрутка где-то внутри | 108 |
| …прокрутки нет вовсе | 42 |
| Экранов, где без прокрутки ≥ 540 dp (обрежет на Титане в портрете) | **17–20** |
| Экранов, где без прокрутки ≥ 220 dp (обрежет в альбомной) | **53–59** |
| Размеры: через `@dimen` / числом в разметке | 9402 / 400 |
| `textSize` в dp / в sp | 1424 / 523 |

Две цифры через тире: в первой скрытые при старте блоки не учтены, во второй учтены.

- **Квалификаторы есть только у библиотек.** В `layout-land` (6 файлов), `layout-sw600dp` (3),
  `values-sw600dp` (17 размеров), `values-land` (19) лежат только файлы Material/AppCompat.
  Своих планшетных или альбомных ресурсов у Трибита нет.
- **`@dimen` ничего не адаптирует.** 380 размеров `dp_N` и 29 `sp_N` — это просто N dp
  (`values/dimens.xml`: `dp_10` = `10.0dip`), и ни в одной папке-квалификаторе они не переопределены.
  Вся адаптация — это AutoSize.
- **Три четверти текста задано в dp** (1424 против 523): системный размер шрифта на него не действует.
- **Ложный отступ под статус-бар.** Шапки многих экранов сдвинуты вниз вручную на `marginTop=@dimen/dp_44`
  (например, `activity_device_control_56`, `activity_eqlist_56`). На Титане это 188 px при настоящем
  статус-баре 48–96 px, то есть лишняя полоса.
- **Кнопки уходят под навигационную панель.** При `targetSdk 36` на Android 16 приложение обязано
  рисовать от края до края. Отступ под панель ставит только `BaseActivity.setBottom()`
  (`base/BaseActivity.java:211–219`), а вызывают его 70 экранов из 146 (`grep -rl "setBottom();"`).
  Высоту панели метод берёт через ресурсы приложения (`:181–187`), а их плотность переписала AutoSize,
  поэтому на Титане отступ выходит примерно вдвое больше нужного.

### 3.2 «Connection failed» и переподключение (жалоба № 1, 366 отзывов; № 25, 30 отзывов)

**а) Повтор подключения мёртв в 16 экранах из 17** (`s2_reconnect.py`). В `Bts56ControlActivity.checkedToConnect`
(`:2120`) стоит защита `if (isConnecting) return;` (`:2121`). При ошибке (`:2179–2184`) код уменьшает счётчик
`reconnect`, показывает «Reconnecting» и через 200 мс снова зовёт `normalReconnect` → `checkedToConnect`
(`Bts56ControlActivity$checkedToConnect$1$1.java:41,50`). Но `isConnecting` перед повтором **не сброшен**,
и повтор сразу выходит. Обещанные три попытки не делаются ни разу. «Reconnecting» висит 3 с (`$1$2.java:40,49`),
потом исчезает, а `isConnecting` остаётся `true`. Теперь и автоматическое переподключение по событию
системы (`onConnected` → `normalReconnect`, `:1945–1955`) молча ничего не делает, пока экран не закроют.
Та же ошибка в `BtsControl12/20/36/51/52/58Activity`, `BtsControlNewActivity`, `BtsControlFragment`
и восьми экранах таймеров и голоса (список в выводе скрипта).

**б) Повтор глушит антидребезг в `BtClient`.** `BtClient$connectDevice$1.java:92–108`: если тот же адрес
подключали меньше 5 с назад (`CONNECT_DEBOUNCE_MS = 5000L`, `BtClient.java:189`), поток отдаёт только
«загрузку» и завершается. Нет ни «подключено», ни «ошибки», и экран ждёт вечно. Даже исправленный
повтор через 200 мс попадёт сюда, если первая попытка упала быстро.

**в) Ни одной повторной попытки на уровне сокета.** `BtClient.connectReadThread` (`BtClient.java:685–710`)
делает одну попытку `createRfcommSocketToServiceRecord(uuid).connect()`. Без повтора и без запасного
`createInsecureRfcommSocketToServiceRecord`, хотя в их же `SppConnector.java:147` такой вариант есть.
Сразу после сопряжения первая попытка RFCOMM на Android часто падает. В поиске
(`DeviceSearchingActivity.java:1254–1260`) первая же ошибка ведёт в `connectFailed` (`:1731`) и в окно
«Connection Failed» (`:1751`, `DialogDefault.showConnectFailedDialog`), которое предлагает только написать
отзыв в поддержку.

**г) Короткий обрыв выкидывает с экрана.** `onConnected(device, false)` (`Bts56ControlActivity.java:1945`)
вызывает `blueDisconnect()`, а он сам показывает панель «нет Bluetooth» с кнопкой переподключения.
Но потом рассылается `ConnectStatus(false)`, и его же обработчик `connectChange` (`:2254–2264`) пишет тост
«Bluetooth disconnected» и делает `finish()`. Это ровно жалоба № 25: «теряет колонку, выкидывает
на главный».

**д) Окна дублируются и утекают.** `DialogDefault` держит окна в статических полях (`DialogDefault.java:97–99`)
с контекстом экрана, а это утечка экрана. Проверка «уже показано» сломана: `if (normalDialog2.isShowing()…)`
(`:192, :329, :425`) спрашивает только что созданное окно, которое всегда закрыто. Каждый вызов кладёт
новое окно поверх старого. Плюс 79 вызовов `DialogManager.dismissAllDialog()` в 61 файле: любой экран
закрывает окна всех остальных.

### 3.3 Зависание на логотипе (жалоба № 4, 159 отзывов)

`FirstActivity.java:151–159` и `FirstNewActivity.java:153–162`: при включённой сети экран старта сначала
запрашивает строки с сервера Трибита и пускает дальше, **только если пришло значение 1**
(`FirstActivity.java:194–196`, `FirstNewActivity.java:180–183`). А `ViewModelFirst` (`modulelogin/viewmodel`):

- ответ без данных ставит **2** (`:81`), и экран висит на логотипе навсегда, показав тост;
- пустой ответ (`json.length() <= 3`, `:91`) не ставит ничего, тоже вечное ожидание;
- нет строк для языка: `map.get(lang)` и `checkNotNull` (`:94`) роняют приложение при старте.

Ответ сервера медленный — логотип висит до таймаута EasyHttp. Владелец запретил запросы к их серверу,
и этот патч его запрет и выполняет. **Патч B:** в обоих экранах условие `NetworkUtils.isConnected()`
заменить на «всегда `showAgree()`». Это два места в smali, `if-eqz` → безусловный переход. Риск низкий:
строки и так лежат в SharedPreferences с прошлого раза.

### 3.4 Главный поток и прочее

- `BtClient.forceDisconnect` (`BtClient.java:1214–1226`) делает `Thread.sleep(500)`. Его вызывают из
  `bleConnectNormal` (`:1062`), а тот вызывается из экранов, то есть на главном потоке. Это полсекунды
  замирания на BLE-колонках (не на Blast 2, у неё классический SPP).
- `Room ... allowMainThreadQueries()` (`database/AppDatabase.java:40`): запросы к базе разрешены
  на главном потоке. Из экранов напрямую не вызывается, риск невысокий.
- `onDataReceived` в `Bts56ControlActivity.java:2083` проверяет `bArr[0] == 0`, а длину смотрит уже потом:
  пустой пакет уронит экран. Чинится тем же патчем F.

## 4. План работ: польза на риск

Размер: XS — до 5 строк smali/ресурса, S — до 30, M — до 100.

| Очередь | Патч | Что чинит | Размер | Риск |
|---:|---|---|:-:|:-:|
| 1 | **A. AutoSize вписывает макет целиком** (`AutoSizeConfig.isBaseOnWidth` → сравнение пропорций) | обрезку 17–20 экранов на Титане, в т.ч. регистрацию, кнопку EQ, подсветку, список EQ; делает альбомную рабочей | S (≈ 15 строк) | низкий: на телефонах формула даёт прежний результат |
| 2 | **B. Старт без ожидания сервера** (`FirstActivity`, `FirstNewActivity`) | вечный логотип, падение на `map.get(lang)`; заодно убирает запрос к их серверу | XS ×2 | низкий |
| 3 | **C. Живой повтор подключения**: `isConnecting=false` перед повтором в 16 местах + `CONNECT_DEBOUNCE_MS` 5000 → 150 | «Reconnecting» без попыток, вечное ожидание после первой ошибки | S (16 × 3 строки + 1 константа) | низкий: так задумал их же автор; от двойного нажатия защищает `BtClient.isConnecting` |
| 4 | **7. BLE без GPS** (`TribitApp` `setNeedCheckGps` 1 → 0, из иссл. 03) | «не находит колонку» на планшетах без GPS | XS | низкий |
| 5 | **F. Сетки от падений на пути Blast 2** (`Bts56ControlActivity:608/614/2083`, `MainNewActivity:1936`, `EqButton56Activity:1104`, `Bts56InfoActivity:1182/1252`) | падения при необычной версии или коротком ответе | S–M | низкий |
| 6 | **D. Не закрывать экран при коротком обрыве** (`connectChange`: убрать `finish()`, панель «нет Bluetooth» остаётся) | жалоба № 25 | XS | средний: проверить, что кнопка переподключения на панели работает |
| 7 | **I. `configChanges` для 16 `*InfoActivity`** (манифест) | обрыв прошивки при повороте | XS | низкий |
| 8 | **G. Окна без дублей**: в `DialogDefault` проверять старое окно, а не новое | стопки «Connection failed» и «нажми в настройках» | S | низкий |
| 9 | **Ресурс: `item_eq_seekbar_new` `dp_232` → ≈ 190** | низ ползунков своего EQ | XS | низкий |
| 10 | **H. Нав-бар**: вызывать `setBottom` из `BaseActivity` для всех экранов или брать высоту панели через `WindowInsets` | кнопки под навигационной панелью у 76 экранов | S | средний: у 70 экранов отступ уже есть, нельзя поставить его дважды |
| 11 | **E. Повтор сокета с запасным insecure-RFCOMM** в `BtClient.connectReadThread` | «Connection Failed» после сопряжения | M (≈ 40 строк) | средний, нужна колонка в руках |
| 12 | **Убрать патч 3** после проверки лога `AndroidAutoSize` на Титане | путаницу: патч ничего не даёт | XS | низкий |

Порядок проверки на Титане: собрать A + B + C + 7 одним APK. Пройти шаги из таблицы раздела 2:
регистрация, список EQ, кнопка EQ, подсветка, затем поворот. Выключить и включить колонку на главной
странице, чтобы увидеть повтор. Лог снимать с фильтром `AndroidAutoSize`, `普通连接`, `connectDevice`.

## Как считалось

Скрипты лежат в `tools/recon/`. Все только читают; запускать из корня репозитория:

```
python -I tools/recon/s1_manifest.py   .                 # ориентация, configChanges, onSaveInstanceState
python -I tools/recon/s2_reconnect.py  decompiled/jadx-base/sources   # мёртвый повтор
python -I tools/recon/s3_layouts.py    .                 # разметки, прокрутка, высоты → layouts.tsv
python -I tools/recon/s3_layouts_nogone.py .             # то же, скрытые блоки учтены (запуск из ng/)
python -I tools/recon/s4_tree.py       work/base/res activity_register_new 3   # дерево разметки
python -I tools/recon/s5_defects.py    decompiled/jadx-base/sources show       # породы падений
python -I tools/recon/s6_textsize.py   work/base/res layouts.tsv               # dp против sp в тексте
```

Разовые проверки через `grep`: `setBottom();` (70 файлов), `fl_main` (66 разметок), значение `IS_NEW_UI_SHOW`
(`constant/SConfig.java:11` = true, значит, старт идёт через `FirstNewActivity` → `LoginNewActivity`).
Ограничения эвристики высот: размер у `RecyclerView` и пользовательских виджетов без явной высоты
считается нулём; цепочки `RelativeLayout` и `ConstraintLayout` разобраны приблизительно. Отдельные
огромные значения (`fragment_device`, `dialog_to_pair`) — артефакты эвристики, на выводы не влияют.
